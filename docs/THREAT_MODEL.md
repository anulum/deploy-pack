# Tooling trust boundaries

Current assets are maintained source, exact metadata/schema/lock identities and scoped infrastructure reports. Reviewed executable policy and its independently pinned schema are trusted. Received JSON values are data and cannot choose an executable, plugin, repository identity or weaker policy.

The implemented boundary refuses duplicate keys, nonfinite values, invalid UTF-8, unpaired surrogates, oversized files and linked/nonregular inputs. Fixed authored diagnostics avoid echoing confidential values. Accepted metadata precedes exclusive complete output creation; verification never replaces an inventory.

The tooling assumes a stable ordinary local filesystem and reviewed environment. It does not sandbox hostile concurrent filesystem changes, operating-system compromise or power loss. Static validation does not qualify package evidence, target compatibility, current trust, action authority or physical recovery.

Future package acceptance requires actual prior artifact/policy/source support and current gates. Per-unit actions require separately authorized target providers, supported acknowledgment/reconciliation and complete observed outcomes. A valid seal cannot replace a missing gate, make stale health current, authorize a device action or establish recovery capability.
